# AAU tool-evidence verifier v1 — trust model and usage

**Status:** deterministic evidence-screening prototype, NOT a physical simulation, specialist engineering certificate or replacement for the frozen 11+5 manual grading rubrics.

## Basis

This verifier has **NO list of preferred software** and **NO hardcoded answers to the power-grid benchmark**. Its external authoritative inputs are:

1. **Original user task bytes**, SHA-256 anchored.
2. **Independently approved requirements manifest** generated by the blind requirements analyst plus separate review, including required scenarios, transitions, criticality and a trace to original task. This source is not the tool-selecting model's own requirements. A verifier CANNOT discover missing requirements purely from the candidate's self-reported list; a domain expert must ensure the independent manifest is complete.
3. **Candidate toolchain proposal** (untrusted model-generated tool IDs, claimed methods/APIs, limits, I/O, independent rejection rules, interface contracts).
4. **Separate evidence registry** maintained outside model write access: reviewed primary-source documentation snapshots and genuine run artifacts (capability probes, contract tests, independent replay), each with exact content SHA-256, reviewer, producer, covered requirement IDs and scenarios.
5. **Frozen external acceptance rubrics** for actual PASS/FAIL. This prototype reports only `BLOCKED` or `READY_FOR_SEPARATE_RUBRIC_REVIEW`; even the latter **NEVER** constitutes passing Stage One or authorizing Stage Two.

## Structural and evidentiary checks

- Every **independent critical requirement** must be covered by an explicit selected tool claim with an identified executable method and typed inputs/outputs.
- Named packages or links without **both** independently reviewed documentation AND actual capability-test evidence are insufficient.
- Every claim needs an **independent** checker with an explicit rejection rule and a saved successful replay proof, not simply acceptance by its own optimizer.
- Every declared tool interface requires a typed unit/identity mapping and an **independent contract test**.
- Checkers must cover **all** scenario IDs and state transitions required by the independent manifest, rather than just the nominal case.
- Artifact digests must match actual evidence files under a trusted root, with traversal disallowed.
- Any invalid provenance, missing critical coverage, inconsistent task SHA, model self-authorization, unsupported methods, or unverifiable claims produces `BLOCKED`.
- No actual tool installation, live software API call, physics calculation or physical-world action occurs in this prototype. It does not mistake syntactic checks for domain truth.

## Explicit trust boundary and limitations

The evidence registry and independent requirements manifest are trusted **because of who is permitted to write/review them**, not because the model says so. Version 1 verifies digests/integrity but **not cryptographic signatures or reviewers' identities**. Production-grade use requires controlled write permissions, author attestations and ideally signing before evidence can become authoritative.

An attacker or an unreviewed model able to alter the evidence registry can forge successful records: therefore it **MUST NOT** be built from the Kimi response by copying its `PASS` labels. All snapshots and probes must originate from a genuinely separate specialist/test runner. The unit tests' successful synthetic case demonstrates only checker consistency, not real tool capabilities.

The doc/registry records require actual primary-source docs reviewed by competent personnel and credible runnable probes. URLs alone are insufficient: the evidence artifact must be fetched/saved/verified independently. Similarly, merely having a `PASS` record does not prove domain/model fidelity—expert review and frozen rubric remain mandatory. The verifier does not currently fetch documentation, execute probes or independently confirm the registry's authorship. Those are later integrations.

**Never route the output of this pre-gate directly to deployment, live control or Stage Two.**

## CLI

```bash
python experiments/tool-selection-restoration/tool_evidence_verifier_v1.py \
  --task path/to/original_problem.json \
  --requirements path/to/independently_approved_requirements.json \
  --candidate path/to/model_tool_proposal.json \
  --registry path/to/independently_produced_proof_registry.json \
  --evidence-root path/to/real_test_and_document_artifacts \
  --out path/to/structural_verifier_receipt.json
```

The CLI exits with status 2 when blocked. Example input fields and fixtures are in `test_tool_evidence_verifier_v1.py`, which uses entirely synthetic record-processing operations; it embeds **no** power-grid or Kimi answer key.

## Tests

```bash
python -m unittest discover \
  -s experiments/tool-selection-restoration \
  -p 'test_tool_evidence_verifier_v1.py' -v
```

15 synthetic tests cover a ready-for-external-review evidence structure (still no Stage-1 pass), omitted requirements, docs-only evidence, model-forged PASS strings, tampered artifacts, missing replays, self-checks, uncovered scenarios and transitions, untested interfaces, wrong task hash, duplicate claim IDs, model trying to authorize Stage Two, untrusted evidence authorship, and path traversal.

## How to incorporate into AAU

- **Before Kimi proposes tools**: independently derive the full requirements inventory from the original problem, reconcile and approve its coverage; do not supply this hidden test answer to the architect.
- **After Kimi proposes tools**: normalize and trace each selected tool operation, interface and independent checker to that inventory.
- **Then**: collect source documentation and execute safe, offline capability probes in an isolated runner, writing reviewable independent artifacts into the restricted evidence registry.
- **Then**: run this deterministic fail-closed evidence pre-gate. If blocked, route specific, factual evidence gaps to remediation. If ready, separately apply original frozen 11-criterion and 5-criterion rubrics with competent technical review. No automated promotion from this prototype to Stage Two.

This is *not* a rerun of K2.6's failed power-grid benchmark; it establishes the verification mechanism needed for a future controlled test without changing historical grades.
